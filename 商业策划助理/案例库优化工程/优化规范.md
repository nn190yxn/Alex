# 优化规范

## 1. 案例卡片标准

每个案例最终形成一张结构化案例卡，字段分为四层：

### A. 项目身份

- `case_id`
- `project_name`
- `aliases`
- `city`
- `country_region`
- `source_case_ids`
- `duplicate_group`

### B. 项目事实

- `project_type`
- `asset_condition`
- `size`
- `space_type`
- `opening_or_operation_stage`
- `developer_operator`
- `business_tags`
- `customer_type`
- `evidence_status`

### C. 商业机制

- `target_problem`
- `operation_goal`
- `core_mechanism`
- `traffic_mechanism`
- `space_mechanism`
- `tenant_brand_mechanism`
- `content_operation_mechanism`
- `revenue_or_asset_effect`

### D. 迁移判断

- `transferable_elements`
- `migration_conditions`
- `migration_difficulty`
- `non_transferable_elements`
- `recommended_project_types`
- `verification_priority`

## 2. 证据状态

| 状态 | 使用方式 | 最低要求 |
|---|---|---|
| `未整理` | 不进入候选结果 | 只有原始标题或片段 |
| `线索` | 内部研究线索 | 有项目名称，但核心事实未确认 |
| `部分核验` | 内部候选，可标注不确定性 | 至少一个可靠来源确认身份，部分机制仍待核验 |
| `已核验` | 可进入客户正文 | 核心身份、核心机制和关键引用均有来源 |
| `不采用` | 禁止引用 | 项目身份不清、来源冲突或与案例库重复且无增量 |

## 3. 来源等级

| 等级 | 来源 | 用途 |
|---|---|---|
| A | 项目方、开发商、运营方、政府、官方统计或官方项目页 | 支撑项目身份、体量、开业、运营动作等核心事实 |
| B | 主流媒体、专业商业地产媒体、行业机构、公开采访 | 补充机制、客群、活动和经营表现 |
| C | 视频转录、社交平台、搜索摘要、转载内容 | 只能作为线索，不单独支撑核心事实 |

同一关键事实优先由 A 级来源支撑；只有 B/C 级来源时，必须标记“部分核验”或“待进一步确认”。

## 4. 核验记录格式

```text
事实：
来源：
来源等级：A/B/C
发布日期：
访问日期：
来源支撑范围：
核验结论：已确认/部分确认/冲突/无法确认
对案例卡的影响：
```

## 5. 禁止事项

- 不将搜索摘要改写为项目业绩；
- 不把“计划、预计、目标”写成已经发生；
- 不把品牌名单写成确定入驻，除非有明确来源；
- 不把案例的城市级资源、独特政策、产权和预算条件直接迁移到本案；
- 不为了填满字段而猜测客群、投资强度或经营结果。
