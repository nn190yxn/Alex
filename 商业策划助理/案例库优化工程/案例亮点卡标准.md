# 案例亮点卡标准

## 目的

把“有来源的项目资料”转化为可用于商业策划的判断单元。每个案例卡必须回答：它真正做对了什么、解决了什么问题、动作为什么有效、什么项目可以借、借到什么程度。

## 准入规则

- `部分核验`：可以填写经来源支持的亮点、机制、可借鉴动作和边界；不得补写来源未支持的经营结果。
- `线索`：只填写身份消歧方向和待验证假设；不得形成可直接引用的项目亮点或成功结论。
- `已核验`：才可作为客户提案中的完整案例。

## 必填字段

| 字段 | 填写要求 |
|---|---|
| project_highlight | 一句可观察的项目亮点，不用“网红、优质、高端”等空泛词。 |
| problem_opportunity | 项目解决的具体问题或抓住的明确机会。 |
| decisive_action | 项目采取的关键动作，写空间、招商、内容或经营动作。 |
| mechanism_chain | 用“条件 → 动作 → 结果/转化”表达，不得跳过中间机制。 |
| evidence_backed_result | 仅填写来源已支持的效果；没有数据则写“经营结果待补”。 |
| transferable_action | 可直接转译到方案里的方法，而非复制项目名称、建筑或IP。 |
| applicability_trigger | 何种项目问题出现时应调用该案例。 |
| required_conditions | 动作成立所需的资产、客群、运营、预算或审批条件。 |
| non_transferable_conditions | 不能照搬的城市资源、产权、交通、自然禀赋、品牌或特殊投入。 |
| proposal_use | 在提案中可用作“策略依据 / 动作参考 / 风险提示”中的哪一种。 |

## 独立案例卡输出

每个 `card_status=已完成` 的案例，必须同步生成一份可独立阅读的 Markdown 卡片，存放于：

```text
案例卡/<case_id>-<project_name>.md
```

卡片固定展示项目身份、证据状态、亮点、问题/机会、关键动作、机制链、已确认结果、可借鉴动作、适用触发条件、成立前提、不可照搬条件、提案用途及来源。卡片只引用该案例自身的证据记录；重复项目会明确标注关联案例ID。

## 质量要求

1. 一个亮点必须对应至少一个来源已确认的动作或事实。
2. “可借鉴”必须写成动作，且同时列出成立条件。
3. 将活动期客流、开业数据、规划和预告明确标记，不能当作长期经营效果。
4. 同一项目有重复案例编号时，案例卡保留原ID，但写明重复关系，后续引用只能选择一个规范项目条目。
5. 每张卡至少形成一条可检索的“问题 → 动作 → 适用条件”链路。
