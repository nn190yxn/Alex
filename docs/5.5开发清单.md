# 5.5开发清单（小程序建设执行版）

## 0. 文档目的
- 将“小程序建设思路”转换为可执行、可验收、可协作的开发清单。
- 本文档面向多 Agent 并行执行，要求每项任务都有输入、输出、验收标准与边界约束。

## 1. 目标与范围

### 1.1 本期目标（MVP）
- 在当前后端能力基础上，上线小程序核心闭环：登录 -> 会员 -> 工具 -> 邀请裂变 -> 支付 -> 返利。
- 与现有 Web/后端共用业务模型与数据库，避免重复建设。

### 1.2 本期范围（P0）
- 账号登录：手机号验证码登录/注册。
- 会员与支付：套餐展示、下单、支付回调、会员生效。
- 工具中心：高频工具入口与权限控制。
- 裂变邀请：邀请码、邀请链接、返利统计、返利明细。
- 用户中心：会员信息、工具使用记录、邀请数据。

### 1.3 延后范围（P1/P2）
- P1：分享海报、返利筛选与导出、消息订阅通知。
- P2：抖音/小红书专项工作台、深度数据看板。

## 2. 强制边界约束（所有 Agent 必须遵守）

### 2.1 架构与数据约束
- 禁止新建第二套用户/订单/返利模型，必须复用现有后端模型：`users`、`orders`、`referral_commissions`。
- 禁止绕开后端直接在小程序端实现支付或返利计算，支付与返利逻辑统一在服务端。
- 禁止修改线上数据库字段语义（如 `member_level`、`order.status`），只允许增量兼容改动。

### 2.2 联调与发布约束
- 本地联调可用 mock，但上线验收必须在真实 MySQL 环境执行一次完整链路。
- 线上环境 `/home/ubuntu/woying-ai` 不是 git 仓库，部署采用文件同步 + PM2 重启。
- 任何触及支付回调/返利逻辑改动，必须附带回归结果（成功/失败与日志证据）。

### 2.3 协作约束
- 并行 Agent 不可同时修改同一文件。
- 每个任务完成后立即更新本清单“执行记录”章节。
- 每次提交必须注明：改动文件、接口影响、回归结果。

## 3. 任务分解（按执行顺序）

### A1. 小程序项目骨架初始化
- 输入：现有前后端代码结构与接口清单。
- 步骤：
  - 初始化小程序工程目录（建议 `miniapp/`）。
  - 建立页面路由：首页、工具中心、会员、邀请中心、用户中心、登录页。
  - 建立 API 客户端层，统一 baseURL、token 注入、错误处理。
- 输出：可启动的空白小程序壳。
- 验收：本地可编译运行；页面路由可互跳。

### A2. 账号登录与会话管理
- 输入：`/api/auth/send-code`、`/api/auth/register`、`/api/auth/login`。
- 步骤：
  - 接入发送验证码与登录/注册流程。
  - 保存 token 与用户基础信息。
  - 实现登录态守卫（未登录拦截敏感页）。
- 输出：完整登录态闭环。
- 验收：新用户注册、老用户登录、token 过期处理均正常。

### A3. 会员与支付主链路
- 输入：`/api/payment/create-order`、`/api/payment/callback`、会员查询接口。
- 步骤：
  - 实现套餐展示与下单。
  - 对接支付唤起与状态轮询。
  - 支付成功后刷新会员信息。
- 输出：会员升级链路可用。
- 验收：订单成功创建、回调成功、会员等级与到期时间正确更新。

### A4. 邀请裂变与返利中心
- 输入：`/api/referral/my-code`、`/api/referral/stats`、`/api/referral/commissions`、`/api/referral/share-link`。
- 步骤：
  - 展示邀请码、邀请链接、返利统计、返利明细。
  - 实现分享动作（文案 + 链接）。
  - 在注册页支持 `ref` 自动注入推荐码并可见化展示。
- 输出：邀请中心页面与注册联动。
- 验收：邀请注册后 `referralCount` 增加；首单支付后返利入账并在明细可见。

### A5. 工具中心与权限控制
- 输入：工具列表、会员等级权限映射。
- 步骤：
  - 按会员等级过滤工具入口。
  - 对未授权工具统一提示与引导升级。
  - 接入工具调用与历史记录展示。
- 输出：可用的工具中心页面。
- 验收：免费/初阶/进阶/高阶账号权限表现一致。

### A6. 线上数据库与环境核验
- 输入：线上服务器、MySQL、Redis、PM2。
- 步骤：
  - 检查 `woying_ai` 库与关键表是否存在。
  - 若缺失执行 `backend/docs/schema.sql`。
  - 核验 `.env` 中支付回调与数据库配置。
- 输出：可用于真实验收的线上环境。
- 验收：`users/orders/referral_commissions` 可查询、可写入。

### A7. 真实环境最终验收（必须）
- 输入：线上运行服务。
- 步骤：
  - 执行链路：推荐人注册 -> 获取邀请码 -> 被邀请人注册 -> 下单 -> 支付回调 -> 查询返利统计/明细。
  - 记录接口返回、日志时间点与数据库落库结果。
- 输出：最终验收报告。
- 验收：返利金额=订单金额*20%，明细状态为 `pending`，统计与明细一致。

## 4. 验收口径（统一标准）

### 4.1 功能验收
- 登录、会员、支付、邀请、返利五条链路均可独立跑通。
- 主流程失败必须返回可读错误，不允许静默失败。

### 4.2 数据验收
- `orders`：订单状态与支付时间正确。
- `users`：`member_level` 与 `member_expire_at` 正确更新。
- `referral_commissions`：唯一订单约束生效，返利金额精度正确。

### 4.3 回归验收
- 返利文案保持“返利不设上限”。
- 邀请入口可从首页/会员页/用户中心到达。
- 注册页推荐码展示可见，避免用户误判未生效。

- Agent-3：测试与验收脚本、日志归档（A7 + 验收报告）。

## 8. 接口契约锁定（避免前后端扯皮）

### 8.1 不可变字段（本期锁定）
- `GET /api/referral/stats`：`referralCode/referralCount/commissionRate/commissionSummary/referredUsers`
- `GET /api/referral/commissions`：`order_id/order_amount/commission_rate/commission_amount/status/pending_until/referred_nickname`
- `POST /api/payment/create-order`：`orderId/payUrl/amount`
- `POST /api/payment/callback`：`orderId/status/sign`

### 8.2 兼容策略
- 只能新增字段，不能删除或重命名已有字段。
- 若必须变更字段，先新增兼容字段，待前端切换后再删除旧字段。
